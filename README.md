# Nyaa猫猫语音

让 QQ 机器人按需用 **TTS 语音**回复，其余情况一律文字回复。

## 功能

插件提供两种触发语音回复的入口，两者共用同一条 TTS 执行链路：

| 入口 | 判定方式 |
|---|---|
| **用户要求语音** | 对话 LLM 读取工具 `reply_with_voice` 的说明后自主判断（语义理解，非关键词匹配） |
| **用户以语音输入** | 检测用户本条消息（或其引用的消息）是否为语音消息，命中后直接激活 |

**默认行为**：用户既没要求语音、也不是语音输入时，**一律文字回复** —— 插件不改变机器人的默认行为。

## 与 AstrBot 全局 TTS 开关的区别

AstrBot 全局设置中的「启用文本转语音」开关是**会话级持久开关**，打开后**每条回复**都会变成语音。

本插件**不使用该开关**，而是：

- **自行取 TTS provider 实例并调用其合成接口**，绕过全局开关独立工作
- **不写入任何持久状态** —— 判定结果通过事件级临时标记传递，**仅当条消息生效**，天然一次性

## 实现要点

### 执行链路

```
① LLM 调用 reply_with_voice 工具  ┐
                                  ├→ 打事件级标记
② 检测到用户语音输入              ┘
                                        ↓
                        发送前钩子读取标记
                                        ↓
                取 TTS provider → get_audio() → 替换为 Record 语音段
```

### 语音输入的判定

判定依据是**平台原始消息（`raw_message`）中的 `record` 段**，而非 AstrBot 的消息链组件。

原因：AstrBot 的 `PreProcessStage` 会对语音消息执行 STT，**并把消息链中的 `Record` 组件原地替换为 `Plain`**，之后便无法再通过组件类型识别。而平台原始消息不会被该过程改动。

### 触发时机

- `on_llm_request`：在 LLM 请求前做语音输入检测（此时 STT 已完成，但原始消息仍可读）
- `on_decorating_result`：在消息发送前把文本替换为语音

## 安装

1. 将本插件目录放入 AstrBot 的 `data/plugins/` 下
2. 重启 AstrBot
3. 无需任何配置

## 依赖

- AstrBot `>=4.0.0`
- 一个可用的 TTS 提供商（在 AstrBot 的「服务提供商」中配置，插件会自动选取）

> 注意：本插件会自动选取 TTS provider，因此需要在 AstrBot 中**至少配置一个 TTS 提供商**。若一个都没有，插件会静默降级为文字回复，不影响正常使用。

## 使用示例

**触发语音回复：**

```
用户：用语音回复我，今天天气怎么样
用户：（发送一条语音消息）
用户：（@机器人 并引用一条语音消息）
```

**不触发（保持文字）：**

```
用户：今天天气怎么样
用户：你声音好听吗
用户：我刚才发了条语音
```

## 日志与排障

插件运行时会输出以下日志：

```
[NyaaVoice] 用户语音输入，已激活语音回复        ← 命中语音输入
[NyaaVoice] 已标记语音回复, umo=...             ← LLM 调用了工具
[NyaaVoice] 已替换为语音消息: <路径>            ← 成功转为语音
[NyaaVoice] 无可用 TTS provider，降级为文字     ← 未配置 TTS
```

**若语音未发出**，请依次检查：

1. AstrBot 中是否配置了 TTS 提供商
2. 日志中是否出现「已标记语音回复」或「已激活语音回复」
3. 日志中是否出现「已替换为语音消息」
